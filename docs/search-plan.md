# Search on top of the main site's Elasticsearch index

Status: **plan, nothing built.** Findings were measured against the live site on 2026-11-17. An earlier
draft of this file got transcripts and Instant Results wrong; this version is corrected, and says where
something is still unexplained.

## What exists today

`SiteSearch` and the Episode Archive filter both call `/api/episodes?query=`, which filters the merged
episode list in memory (`lib/episodes/filter.ts`, `matchesQuery`): title, description and guest names only.
It cannot see show notes, transcripts or blog posts, and it has no ranking.

## What the WordPress site already has

communitycode.dev runs **ElasticPress against a hosted ep.io index** with autosuggest, Instant Results,
highlighting and facets (post type, category, tag).

- **Transcripts are in the index, on the episode.** An episode document carries `transcript_content`
  alongside `post_title`, `post_content_plain`, `permalink`, `post_name`, `post_type`, `thumbnail`, `terms` and
  `meta`. A search for "eventually" returns 24 hits across posts, pages and episodes (Episode 23 among them).
- **The autosuggest endpoint is public and works server-side.** The page ships its URL and the full ES query
  template (`epas.endpointUrl`, `epas.query`, with a placeholder for the search term). POSTing that template
  with the term filled in works from curl with **no Origin header and no credentials** (200). It returns
  `_score`, `_source` and title/content/excerpt highlights.
- **It only accepts the plugin's own template.** A hand-written query (a different field list, a
  `transcript_content` highlight) gets `403`. So we can reuse the template but cannot ask for transcript
  snippets from ES. Treat that as a deliberate lock, not something to work around.
- **Core REST search is also ES-backed** (`x-elasticpress-query: true` on `wp/v2/search`,
  `wp/v2/episodes?search=`, `wp/v2/posts?search=`) and needs no template. But it is a different query:
  "eventually" returned 2 episodes there, against the autosuggest template's wider set. I don't know why;
  until that's explained, don't treat core REST search as equivalent.
- **Instant Results (`community-code/v1/ep-search`) behaves differently by session.** In a logged-out Chrome
  session and from curl it answers `500 ep_proxy_error: "EP endpoint not configured."`, and the overlay stays on
  "Loading results". It works for the site owner. Unexplained: possibly login state, or a response cached at the
  edge (`cache-control: public, max-age=604800` is sent even on the 500). Worth ruling out before relying on it.
- **Edge caching:** REST responses are cached for a week per URL. Reuse the `?cb=<bucket>` trick from the feed
  for anything that has to see new content.
- **The index is named `pantheon-se-demo-1-...`.** The owner believes that is an old index and has not yet
  validated it. The endpoint URL and index name come from the page config, so a change on the WordPress side
  changes them; do not hardcode either.
- Bot protection still applies to the WordPress host; fetches must send `WP_USER_AGENT` (the existing `wpFetch`).

## Options

**A. Call the autosuggest endpoint server-side with the plugin's template.** `lib/search.ts` + `/api/search`
POST the template (term substituted) to the endpoint, map each hit to our own types (episodes by `post_name`,
posts/pages by `permalink`), and build the snippet locally by finding the term in `transcript_content`.
Gets ES ranking, transcripts and blog in one request. Costs: the template has to reach us (below), `_source`
cannot be trimmed so each response includes full transcripts (large), and highlighting is title/content only.

**B. A `community-code/v1/search` endpoint in the WordPress repo** (it already owns `/contact`, `/newsletter`).
Runs the query inside WordPress with `_source` filtered, transcript highlights and facet counts. Best result
quality and smallest payloads; needs a change and deploy in the WordPress repo. It could also fix `ep-search`.

**C. Core REST search.** No template needed, but results differ from the ES template (see above) and carry
no snippets or scores. Fallback only.

**D. The in-memory filter.** Keep as the fallback when ES is down, and for season/type filtering of the
38-item list, which needs no ES.

## Getting the template to the Next app (the open problem for A)

The query template is generated by the plugin from its weighting settings, so it changes when those do.
1. **Expose it from WordPress** (a tiny read-only route, or fold into B). Cleanest.
2. Scrape `epas` from a WordPress page at runtime and cache it. Works today, breaks if the markup changes.
3. Commit a copy to `site.config.ts`. Simplest, and goes stale silently when weighting changes.

## Recommendation

1. **Phase 1:** A, with the template from option 2 behind a cache and a visible failure (not a silent stale
   copy), falling back to D when ES or the template is unavailable. `SiteSearch` and the archive `query` both
   use `/api/search`. Cap the query length and reuse the form-route rate limiting; route status follows the
   existing convention (501 unconfigured, 502 upstream failure).
2. **Phase 2:** B in the WordPress repo, then switch the Next side to it and drop the template scraping.
3. **Phase 3:** facets (season, type, tag), and transcript deep links: find the match in the VTT we already
   parse (`lib/transcript.ts`), link to `/episodes/{slug}?t=<seconds>`, and have the native transcript honour `t`.

## Decisions needed

- A first (needs the template), or go straight to B?
- Include blog posts and pages, or episodes only?
- Is the `pantheon-se-demo-1` index the one to build on? Validate before anything depends on it.
- Why does `ep-search` 500 for a logged-out session? Rule that out on the WordPress side.

## Risks

- Large payloads from A (full transcripts in `_source`) on every query. Cache per term, and cap results.
- The template changing underneath us. Fail loudly and fall back, do not serve stale results as fresh.
- Query text is user input sent to an upstream: cap it, never echo upstream error bodies, and rate limit.
